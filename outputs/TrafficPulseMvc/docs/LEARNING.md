# איך לקרוא ולהסביר את הקוד

## הדוגמה הראשונה: צפייה במקטעי כביש

משתמש פותח `/Traffic/Index`. ניתוב MVC בוחר את `TrafficController.Index`.
`[Authorize]` מחייב משתמש מחובר לפני שהפעולה רצה.
הקונטרולר מבקש מידע מ־ITrafficRepository ובונה DashboardViewModel.
`return View(model)` מעביר את המודל ל־Views/Traffic/Index.cshtml.
Razor מריץ את לולאת foreach בשרת, מייצר HTML ומחזיר אותו לדפדפן.

אין כאן fetch ואין JavaScript שצריך ללמוד. טופס שולח בקשה חדשה לשרת.

## מה עושה Repository

`TrafficRepository` מקבל `TrafficDbContext` בבנאי, בדיוק כמו שה־Repository בדוגמה קיבל ElasticsearchClient.
במקום לכתוב SELECT, כותבים למשל:

```csharp
return _context.Roads
    .AsNoTracking()
    .OrderBy(road => road.Name)
    .ToListAsync();
```

`Roads` הוא DbSet. `OrderBy` ממיין. `AsNoTracking` אומר שהקריאה אינה מיועדת לעדכון.
Pomelo מתרגם את הביטוי ל־SQL; `ToListAsync` מבצע את הבקשה.
`await` אינו יוצר thread חדש לכל פעולה: הוא מאפשר להמתין לפעולת I/O בלי לחסום את thread הבקשה.

## Model לעומת ViewModel

Road הוא מידע שנשמר בטבלה. RoadEditViewModel מכיל רק את השדות שהטופס רשאי לשלוח.
RegisterViewModel אינו מכיל Role. לכן תוקף לא יכול להפוך למנהל באמצעות הוספת Role=Admin לטופס.
השרת בוחר במפורש User בזמן הרשמה.

## למה ממשק

הקונטרולר תלוי ב־ITrafficRepository. בהרצה רגילה מממש אותו TrafficRepository, ובהדגמה DemoRepository.
לכן אותו Controller ואותו View עובדים בשני המצבים. אין if של מצב הדגמה בכל מסך.
המתאם המקומי נועד ללימוד בלבד והוא מסומן; חמש הטבלאות האמיתיות מוגדרות ב־DbContext וב־Migrations.

## בקשה לשינוי נתונים

טופס POST מוסיף אנטי־CSRF דרך Tag Helper. הפילטר הכללי בודק את הטוקן לפני הפעולה.
DataAnnotations מסמנות שדות חובה וטווחים. Controller בודק ModelState.IsValid.
Repository בודק כללים כמו מקטע קיים והתנגשות גרסה.
לאחר שמירה מפנים ב־Redirect לפעולת GET, כדי שרענון הדפדפן לא ישלח את הטופס שוב.

## הרשאות

סיסמה עוברת PasswordHasher, ואינה נשמרת בטקסט גלוי.
התחברות מוצלחת יוצרת עוגייה מוגנת של ASP.NET Core. התפקיד נכתב על ידי השרת.
בכל בקשה נבדקים מצב המשתמש ו־SecurityStamp מול המאגר.
`[Authorize(Roles = "Admin")]` חוסם גישה לפעולות ניהול גם בלי קשר לכפתורים באתר.
עדכון stamp בזמן השבתה מונע שימוש בעוגייה ישנה גם לאחר הפעלה מחדש של המשתמש.

## Kafka — הסיפור המלא

Producer מבקש מדידה מהספק, יוצר JSON ומפרסם עם RoadId בתור Key.
אותו מפתח שומר סדר בתוך partition של מקטע. מזהה המדידה נשמר גם בניסיון חוזר.
Consumer קורא JSON, מבצע validation, מפעיל Repository ושומר מדידה והתרעה באותה טרנזקציה.
רק אחרי הצלחה הוא קורא Commit ב־Kafka.
אם קרס אחרי שמירה ולפני Commit, ההודעה תגיע שוב. המפתח הראשי של Readings מונע כפילות.
הודעה לא תקינה נשלחת ל־dead-letter topic עם סיבה; רק אחרי אישור כתיבתה מאשרים את המקור.
בתקלה של מסד הנתונים ההודעה אינה מאושרת, והצרכן חוזר לאותו offset.

זו התנהגות at-least-once עם שמירה idempotent. לא טוענים ל־exactly-once בין Kafka ל־MySQL.

## האלגוריתם

1. לא מנתחים חריגה על סמך נתון עם אמינות נמוכה מסף ההגדרות.
2. דיווח סגירה יוצר התרעה ללא צורך בהיסטוריה.
3. בוחרים היסטוריה של אותו מקטע ומקור נתונים, ימים קודמים, אותו יום בשבוע וחלון שעה דומה.
4. אם מספר המדידות קטן מהמינימום, לא מסיקים חריגה סטטיסטית.
5. מחשבים ממוצע וסטיית תקן מדגמית.
6. סף הירידה הוא המקסימום בין ירידה מינימלית בקמ״ש ובין sigma כפול סטיית התקן.
7. מהירות נמוכה מהממוצע פחות הסף יוצרת התרעה, עם הסבר ומספר מדידות.

דוגמה: ממוצע 60, סטיית תקן 4 ו־sigma=3 נותנים סף ירידה 12. מהירות 40 יוצרת התרעה.
אם סטיית התקן אפס, משתמשים בירידה המינימלית; אין חלוקה באפס.
אין כאן מודל למידת מכונה ואין הבטחה לחיזוי פקקים.

## חלוקת עבודה לשני חברי צוות

| אחריות ראשית א׳ | אחריות ראשית ב׳ |
|---|---|
| Controllers, Views, ViewModels | Producer, Consumer וחיבור לספק |
| הרשמה, כניסה והרשאות | AnomalyService ומקרי קצה |
| Users ו־Favorites ב־DbContext | Roads, Readings ו־Alerts ב־DbContext |
| בדיקות HTTP ואבטחה | בדיקות אלגוריתם ואמינות מסירה |

שניכם מסבירים את הזרימה המלאה. החליפו תפקידים בסקירת קוד: כל אחד מסביר קובץ של השני ומבצע בו שינוי קטן.
